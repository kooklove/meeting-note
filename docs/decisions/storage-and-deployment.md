# 저장 방식과 배포 대상

## Decisions

- 회의록 데이터는 서버 프로세스의 메모리(`lib/meeting-notes/store.ts`의 `Map`)에만 둔다. 외부 데이터베이스나 캐시 서버를 두지 않는다.
- 이 앱은 상시 켜져 있는 단일 프로세스(사내 서버)에 배포하는 것을 전제로 한다. Vercel 같은 서버리스 다중 인스턴스 플랫폼은 실사용 배포 대상이 아니다.
- Vercel 배포는 데모나 화면 확인 용도로만 쓴다. 그 위에서 실제 회의록을 만들고 참석자를 초대하는 흐름은 보장하지 않는다.

## Boundaries

- 이 결정은 저장소 구현(인메모리 vs 외부 스토어)과 배포 대상(상시 프로세스 vs 서버리스)에만 적용된다. 데이터 모델이나 API 형태를 바꾸지 않는다.
- 사내 서버에 배포하는 한 이 결정은 그대로 유효하다. 사내 서버를 여러 대로 늘리거나 로드밸런서 뒤에 여러 프로세스를 두게 되면 같은 문제가 재발하므로 그 시점에 다시 본다.

## Why

Vercel의 서버리스 함수는 API 라우트 요청마다 여러 인스턴스로 나뉘어 실행될 수 있고, 인스턴스마다 메모리가 분리되어 있다. `globalThis`에 캐시한 인메모리 `Map`은 프로세스 하나에서만 유효하므로, 회의록을 만든 인스턴스와 그 회의록을 조회하는 인스턴스가 다르면 "찾을 수 없음"이 뜬다. 실제로 같은 회의록 링크에 연속 요청을 보내 200과 404가 번갈아 나오는 것을 확인했다.

PRODUCT.md는 애초에 "서버를 사내에만 설치"한다고 전제하고 있다. 이 프로젝트는 수업 제출용이라 사내 시스템에 접근할 수 없고, 사내 서버에 실제로 올려볼 방법도 지금은 없다. 외부 스토어로 전환하면 근본적으로 해결되지만, 실시간 반영(SSE)의 pub/sub 구조까지 함께 재설계해야 해서 이 프로젝트의 범위를 크게 넘어선다. 지금은 원래 전제(상시 단일 프로세스)를 지키는 쪽을 택하고, Vercel은 화면 모양만 보여주는 용도로 한정한다.

## Reconsider when

- 사내 서버에 실제로 배포할 수 있게 되어 상시 프로세스 배포가 현실이 될 때. 그때는 이 결정이 그대로 유지된다.
- 여러 명이 실제로 함께 쓰는 배포 환경이 필요해지고, 그 환경이 서버리스이거나 다중 인스턴스일 수밖에 없을 때. 그때 외부 스토어 전환을 다시 검토한다.

## Still-rejected alternatives

- Vercel KV나 Postgres 같은 외부 저장소로 전환 — 근본적으로 해결되지만 SSE pub/sub 구조까지 다시 설계해야 해서 지금 범위를 넘어선다. 서버리스 배포가 실제로 필요해지면 다시 본다.
- Vercel의 인스턴스 재사용 설정(Fluid Compute 등)으로 완화 — 빈도를 줄일 뿐 근본 해결이 아니고, 언제 다시 어긋날지 보장할 수 없다.

## Evidence worth preserving

- 같은 slug(`20260827_1618_tt`)에 연속 6회 요청을 보낸 결과: 200, 200, 404, 404, 404, 200. 같은 링크인데 응답하는 인스턴스에 따라 결과가 갈린다는 것을 보여준다.
